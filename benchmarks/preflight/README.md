# `otelwrench preflight` on a synthetic exporter upgrade

Inputs: [`examples/preflight/`](../../examples/preflight/), all synthetic and fictional: two
`/metrics` captures of an imaginary `checkout-api` before and after an exporter upgrade, a
Grafana-style dashboard (8 panels) and a Prometheus rule file (4 alerts, 2 recording rules).
The oracle, [`expected.json`](../../examples/preflight/expected.json), labels each of the 14
queries by hand from what the upgrade does to the series it reads; it is not generated by
otelwrench.

Run from the repository root (needs the core dependencies, for example after
`pip install -e .`):

```sh
python3 benchmarks/preflight/run.py            # print the result
python3 benchmarks/preflight/run.py --write    # also rewrite results.json
```

[`results.json`](results.json) is the recorded run. `tests/preflight/test_preflight.py`
re-runs it and compares. No network, no timing, no randomness.

## Result

| View of the same upgrade | Verdict | What it tells you |
| --- | --- | --- |
| Syntax only (both captures parse with `prometheus_client`, as a scrape would) | accepted | nothing: 0 of 14 queries flagged |
| `otelwrench promdiff` alone | fail: 8 failures, 7 warnings | 4 families "removed", 3 "added", 2 label-set changes, 1 type change, growth over budget |
| `otelwrench preflight` with the dashboard and rule file | fail: 8 errors, 2 warnings | 3 of the 4 "removed" families are OTLP suffix renames (one also ms to s), 1 label rename, 1 real removal, 1 type change, growth traced to one label |

Against the oracle, `preflight` flags **9 of the 9 broken queries** (5 of 8 panels, 3 of 4
alerts, 1 of 2 recording rules) and **none of the 5 working ones**. The growth (27 → 45
series, +66.7%, budget 20%) is traced to `rpc_client_calls_total` gaining
`net_sock_peer_port` (0 → 12 values); `cardinality` confirms that dropping it with
`metric_relabel_configs` would merge 24 series into 2, so it has to be aggregated at the
source.

The follow-up commands the report prints work as printed: with the emitted rename map,
`otelwrench promdiff` still fails on the 4 real problems (removal, type change, new label,
growth); adding the emitted allowlist makes it pass.

## Limits

- One hand-built example. It shows the mechanism and that the follow-up workflow runs; it is
  not a precision or recall estimate for real exporters, dashboards or users.
- Query matching is by name (metric and label identifiers outside strings and range
  selectors), not a PromQL evaluation. A query that reads a changed family is flagged even
  if it would still return data by accident.
- Rename detection needs a removed and an added family of the same type whose names the
  `prom-names` rules map onto each other; label renames need one label out, one label in
  and identical observed values. Anything else is reported as a removal or label change.
